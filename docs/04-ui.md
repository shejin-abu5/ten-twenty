# The UI — pages, components, and the design decisions

Craft is 15% ("looks like something a director would open willingly"), product
judgement another 20% ("answers the question without being asked twice").

## Stack choices

- **Next.js 16 App Router, server components.** Pages read SQLite directly — no
  API layer, no client-side fetching, no loading spinners for data. Client
  components exist only where there's genuine interactivity: the period filter,
  the upload form, the assumptions form, the CSV button.
- **Tailwind v4 + shadcn/ui.** shadcn gives accessible Radix primitives (select,
  checkbox, table) as source in the repo rather than a dependency, so they can be
  adjusted. The neutral base palette suits a finance tool.
- **Light theme only, deliberately.** shadcn ships a `.dark` class variant but
  nothing toggles it. A single committed look beats a half-tested second one.

## Period filtering lives in the URL

`?year=2025&month=3`. Not component state. Consequences:

- Refresh keeps the view.
- A filtered view is a link you can paste into an email.
- The server renders the filtered data directly — no client round trip.

`resolvePeriod` defaults to the **most recent year with data** when no params are
present. Opening the app to an empty screen asking to be configured is not an
answer to "did we make money".

The `PeriodFilter` component takes the years and months as props rather than
calling `useSearchParams`, which avoids the Suspense boundary Next requires for
that hook.

## The DataTable

One component, used by every table, defined by columns:

```ts
interface Column<Row> {
  key: string;
  header: string;
  align?: 'left' | 'right';
  value: (row: Row) => CsvValue;   // the raw value
  render?: (row: Row) => ReactNode; // the richer cell
}
```

**The point of the split:** the CSV export is built from `value`, the on-screen
cell from `render`. One column definition drives both, so the export can never
drift from what's displayed. That's the whole CSV stretch goal, for about forty
lines.

`DataTable` is a server component; it passes the derived `string[][]` matrix to a
small client component that builds a Blob and clicks a link.

## Typography and number formatting

Financial tables are mostly about columns of numbers lining up.

- `font-variant-numeric: tabular-nums` on every table, so digits are fixed-width.
- Hours always carry **one decimal** (`minimumFractionDigits: 1`). The first
  screenshot showed `1,641` next to `1,634.6`; the column read as ragged. Fixed.
- Money is AED with no decimals, except the reconciliation note which shows two —
  the brief says "to the dirham", so that one figure has to be exact.
- `null` renders as an em dash, never `0%`. A missing margin and a zero margin
  are different facts.

## Colour

I used the dataviz guidance and actually ran the checks rather than eyeballing.

Profit/loss are **status colours on text**, not two series in a chart, so the
right test is WCAG text contrast, not categorical CVD separation. Both clear
4.5:1 against their surface in each mode (light green 4.97:1, light red 5.16:1).

The safeguard is that **colour is never the only signal** — every coloured figure
sits next to its own signed number, and the margin bar always has its percentage
beside it. That satisfies the "status colours ship with a label, never colour
alone" rule.

Only losses are coloured in tables. Painting every healthy number green turns a
table into a traffic light and hides the two rows that need attention. Headline
KPI figures use `emphaticToneOf`, which colours both directions — that's one
number, not a column.

## Charts — two, and only two

The guidance is explicit that sometimes the answer is not a chart.

1. **Hours per category** — horizontal bars. Single measure, single scale, so one
   hue and no legend; internal categories are faded, billable are solid; every
   bar is directly labelled with hours and share.
2. **Margin** — a diverging bar around a zero midpoint, clamped to ±100% so one
   −112% project can't flatten the column.

Everything else is a table, because eleven projects don't need a scatter plot and
the brief asks for legible tables.

## Honest states

Every page handles four situations:

1. **No data at all** → `NoDataState`, pointing at the Data page.
2. **Data, but none in this period** → a specific message naming the period.
3. **Data with gaps** → the amber `GapsPanel`, collapsed, listing every gap
   sorted by how much is at stake.
4. **A project with no price** → an explicit banner on its page saying what has
   been costed and what to do about it.

The `ReconciliationNote` sits at the top of the dashboard and the assumptions
page. It has three states: balanced, balanced-but-some-cost-reached-
no-project (amber), and genuinely out (red).

I fixed its wording after seeing it on screen with a part-loaded year: the heading
said "Costs reconcile to payroll" while the body reported 216,000 unabsorbed,
which reads as a contradiction. It now leads with the unabsorbed figure when
there is one, and says "Across all loaded data" because it's a whole-dataset
statement sitting next to a single-month KPI row.

## Page-by-page reasoning

- **Dashboard** — KPI row, health, best/worst margin cards, projects sorted
  **worst margin first** (the losses are the thing you need to see), then trend
  and departments. The worst-margin card is the single most valuable thing on the
  page for this dataset.
- **Projects** — whole list. Price is whole-contract; hours/cost/revenue are the
  filtered period. Stated in the table description.
- **Project detail** — whole-life figures, because the price is whole-life. The
  per-person table's revenue shares sum to exactly the price, which is a good
  thing to point at.
- **Productivity** — includes a "never billable" tile naming the people who
  touched no client work. That is a question leadership actually asks.
- **Categories** — bar chart, detail table, and the person × category pivot
  (the stretch goal, because it's the thing finance builds by hand).
- **Departments** — list and drill-down. Both note that a department showing zero
  cost isn't free; its time is in the indirect pool.
- **Data** — upload, the re-upload rules written out, and the parse history.
- **Assumptions** — billable categories (with hours next to each, so you can see
  what you're about to move) and overhead.
